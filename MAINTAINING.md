# Maintaining the Retrac Labs Website

This site is a React + Vite app. If you are used to plain HTML/CSS/JS, the main shift is this:

- HTML is mostly generated by React components.
- Reusable page sections live in `src/app/components/`.
- Project text/content lives in `src/app/data/projects.ts`.
- That same file decides the order projects appear in, and which ones are public at all.
- Styling is mostly Tailwind classes written directly in `.tsx` files.
- The local dev server is Vite, started with `npm run dev`.

## Daily Workflow

1. Open the project in WebStorm:

   ```text
   ~/Websites/retraclabs.github.io
   ```

2. Start the dev server:

   ```bash
   npm run dev
   ```

3. Open the local URL Vite prints, usually:

   ```text
   http://localhost:5173/
   ```

4. Edit files in WebStorm. Vite should refresh the browser automatically.

5. Before committing, run:

   ```bash
   npm run build
   ```

6. Commit and push in GitHub Desktop.

The browser entry shell. You rarely edit this. It contains:

### `src/app/App.tsx`

This is the main traffic controller. It decides whether to show:

- the homepage
- an individual project page
- the beta signup page

## Editing Homepage Sections

### Hero / Big Opening Animation

Edit:

```text
src/app/components/Hero.tsx
src/app/heroChoreography.ts
```

`Hero.tsx` draws the big RETRAC / LABS wordmark and the scroll cue under it.
`heroChoreography.ts` holds the numbers, because App.tsx needs the same numbers
to know when to bring the menu bar in.

As you scroll, the wordmark rushes toward you, blurs, and burns off: the same
move jarredmcarter.com makes. Three values drive it:

```ts
scale    1 → 3.1      // rushes forward
blur     0 → 4.2px    // goes soft
opacity  1 → 0        // burns off
```

To change the numbers, edit `heroChoreography.ts`:

- `HERO_SECTION_VH`: how tall the hero section is, so how much scrolling the
  whole move takes. Bigger means slower.
- `HERO_FADE_END`: how far into that scroll the wordmark is fully gone. `0.8`
  means it finishes at 80%, leaving a short beat of empty screen before the Lab
  arrives.

The menu bar appears the moment the wordmark is gone. That is deliberate; the
two are meant to hand off to each other. `heroDissipatedAt()` is the single
function both files agree on.

To change the scroll cue text, find this in `Hero.tsx`:

```tsx
Specimens Below
```

The arrow under it is a drawn SVG, not a font glyph. It has a real arrowhead.
The older version was a gradient bar that faded out exactly where the head
should have been, which is why there appeared to be no head.

## Editing Project Information

```text
src/app/data/projects.ts
```

```ts
{
  slug: 'amparo',
  name: 'Amparo',
  platform: 'iOS',
  status: 'Available',
  accent: 'pink',
  accentText: 'text-pink-400',
  icon: Smartphone,
  span: 'two-thirds',
  summary: 'A short tagline.',
  description: 'A longer paragraph.',
  highlights: [
    'Bullet one',
    'Bullet two',
  ],
  nextSteps: [
    'Next step one',
    'Next step two',
  ],
  appStoreUrl: 'https://apps.apple.com/...',
}
```

### What Each Field Does

Required on every project:

- `slug`: URL identifier. Example: `#/projects/amparo`.
- `name`: project title, or codename if it is not announced yet.
- `platform`: small platform pill.
- `status`: status pill. Free text, such as "Available", "Beta Testing", or "In Development".
- `accent`: which color row in `src/app/data/accents.ts` the card uses.
- `accentText`: Tailwind text color class.
- `icon`: icon from `lucide-react`. See "Icons" below for finding names.
- `span`: how wide the card sits in the six-column grid. One of:
  - `'full'`: the whole row
  - `'two-thirds'`
  - `'half'`
  - `'third'`

Optional. Leaving these out is meaningful, not lazy. See "Hiding A Project
Until It Ships":

- `teaser`: one plain line saying what the app does. Shown on the card and in
  the beta signup form. **Safe to fill in while a project is still
  unannounced**, and worth doing: it does not announce anything, and a codename
  with nothing attached to it tells a prospective tester nothing. Keep it to a
  function, never a feature list, and never let it name the real product.
- `summary`: large intro text on the card and project page. **A project with no
  summary is treated as unannounced**, regardless of whether it has a `teaser`.
- `description`: main body text on the project page.
- `highlights`: bullets in "What It Is."
- `nextSteps`: bullets in "Next Steps."
- `version`: replaces "Next Steps" with a shipped-versus-coming pair. Use it for
  apps that are actually out:

  ```ts
  version: {
    current: '1.0',
    currentFeatures: ['What you get today', 'And this'],
    next: '1.1',
    nextFeatures: ['What the next build adds', 'And this'],
  }
  ```

  If a project has both `version` and `highlights`, the version pair takes the
  two-column row and "What It Is" moves to a full-width strip underneath.

- `appStoreUrl`: turns the sidebar button into a Download button.

## Reordering Projects

**Move the block. That is the whole job.**

The order of the `projects` array in `src/app/data/projects.ts` is the order the
cards appear on the page, top to bottom. Nothing else needs touching: no card
markup, no index numbers, no `openProject('slug')` calls. Cut a project's whole
`{ ... }` block and paste it where you want it.

The array is deliberately **first in, last out**: the newest and least finished
work sits at the top, and the apps you can actually download anchor the bottom.
Someone landing on the Lab sees what is being built now first, and finds the
shipped apps as the reward at the end of the scroll.

Current order, top to bottom:

```text
Project Salt        (Beta Testing)   ─┐
Project Decibel     (Beta Testing)    │ newest work, nothing announced
Project Deacon      (Testing)         │
Project Cobra       (In Development)  ┘
Snippystack         (Available)      ─┐ shipped, downloadable
Amparo              (Available)      ─┘
```

To put a new experiment at the very top, paste its block above `project-salt`.
To retire something to the bottom, move its block below `amparo`.

### Checking your work

After moving a block, make sure the file still parses:

```bash
npm run build
```

The usual mistake is a missing or doubled comma between `}` and `{`. The build
will tell you the line.

### Adjusting the shape of the grid

Reordering changes the sequence; `span` changes the widths. The grid is six
columns on a large screen, so a row is "full" of any combination adding up to
six:

```text
'full'        = 6   one card, whole row
'two-thirds'  = 4   pairs with 'third'
'half'        = 3   pairs with another 'half'
'third'       = 2   pairs with 'two-thirds'
```

The four codename cards are all `'half'`, so they sit two-by-two. Snippystack
(`'third'`) and Amparo (`'two-thirds'`) share the bottom row. If a row looks
lopsided after a reorder, the spans of that row no longer add to six.

## Hiding A Project Until It Ships

Nothing gets announced before it is finished, beta included. A project is
public only once it has a `summary`.

**To hide a project**, comment out everything from `summary` down. Keep the
`teaser`:

```ts
{
  slug: 'project-salt',
  name: 'Project Salt',
  platform: 'macOS',
  status: 'Beta Testing',
  accent: 'green',
  accentText: 'text-green-400',
  icon: Hash,
  span: 'half',
  teaser: 'File integrity checking. Drag a file in, verify its hash.',
  /* summary: '...',
  description: '...',
  highlights: [],
  nextSteps: [], */
}
```

The `teaser` stays outside the comment on purpose. Saying what an app *does* is
not the same as announcing it, and without that line the card is a codename over
blank space and the beta form asks people to volunteer for something they cannot
identify.

What the site does with that, automatically:

- The card shows the codename, platform, status, and the teaser. No summary.
- The card gets a dashed border instead of a solid one, so it reads as
  deliberately unfinished rather than broken.
- The card is not clickable, because there is no page to open.
- `#/projects/project-salt` typed directly falls back to the homepage.
- The project is left out of "Other Experiments" at the bottom of other pages.

**To announce it**, delete the `/*` and `*/`. That is the only change needed.

The rule that drives all of this is one line at the bottom of `projects.ts`:

```ts
export const isAnnounced = (project: Project) => Boolean(project.summary);
```

### A note on codenames

Codenames are the public name while a project is hidden. When an app is ready to
be announced, change `name` and `slug` to the real name at the same time you
uncomment the copy. Changing `slug` changes its URL, so do not change it after
the app has shipped and people have linked to it.

### Adding a new accent color

If `accent` needs a color that is not already there, add a row to
`src/app/data/accents.ts` and add the name to the `ProjectAccent` type in
`projects.ts`. Tailwind only ships classes it can actually see written out, so
the class names in that file are spelled in full on purpose. Do not try to build
them with a template string like `` `hover:border-${color}` ``, because the color will
silently not appear.

### The glow on a project title card

```text
src/app/components/AccentGlow.tsx
```

The wash of color on a project page's title card. It enters from the top-right
corner, drifts slowly across the card, and keeps gaining intensity for the first
40 seconds somebody is on the page. It is meant to be almost subliminal: nobody
should catch it moving, they should just feel the card was flatter a minute ago.

Two blurred blobs do the work. The first is the project's own `accent`, the
second is the RETRAC LABS gradient at lower opacity so the wash is not one flat
hue. To retune it:

- `RAMP_SECONDS` at the top of the file: how long intensity takes to top out.
- The `opacity` arrays: where it starts and where it settles. The accent blob
  climbs to 0.6, the gradient blob to 0.38.
- The `x` and `y` arrays: where it drifts.

Three things are deliberate and worth not undoing:

- **The two blobs have different periods, 37s and 53s.** Give them the same
  duration and the pair visibly loops.
- **Intensity does not repeat.** It settles at full. A pulse would read as a
  loading spinner.
- **Only `transform` and `opacity` animate.** Animating `left` or `top` on a
  100px-blurred element repaints the whole card every frame. As written it stays
  on the compositor: measured at 8.3ms median frame time with nothing dropped.

**It pauses when the card scrolls out of view.** An IntersectionObserver, via
Motion's `useInView`, calls `pause()` on both animations when the card leaves
the viewport and `play()` when it returns. Pausing rather than stopping is the
point: elapsed time is held, so scrolling away and back resumes the intensity
ramp where it was instead of blooming from nothing a second time.

That is also why the animations are driven imperatively with `animate()` rather
than with `animate` props on a `motion.div`. The declarative form has no pause.

One trap, if you ever refactor this: **`useInView` cannot observe the scope
object returned by `useAnimate`.** Hand it one and it silently reports `false`
forever, the animations pause on mount, and the glow never appears. It needs a
plain `useRef`.

`prefers-reduced-motion` gets a static wash at the old fixed opacity. The card
still has its color, it just does not crawl.

The whole effect is damped to 60% on light backgrounds, where a saturated blur
at full strength turns the card muddy.

## Privacy Policy

Edit:

```text
src/app/components/PrivacyPolicy.tsx
```

**Move the date whenever you change the text.** It is a single constant at the
top of the file:

```ts
const LAST_UPDATED = 'September 13, 2026';
```

"Last updated" is the first thing anyone checks when they want to know whether a
policy still describes what actually happens, so a stale date is worse than no
date. The policy covers the beta program in detail, including what the signup
form collects and who else handles it, so if you change the questions on that
form, change the matching list in the policy in the same commit.

An unannounced project should not be named in the policy either. Project Cobra's
section is commented out in that file for the same reason its copy is commented
out in `projects.ts`; uncomment it at launch.

Footer link:

```text
#/privacy
```

Footer file:

```text
src/app/components/Footer.tsx
```

Privacy policy text should be plain and conservative. Avoid promising things that are not technically guaranteed yet. For health-related apps such as Amparo, avoid language that sounds like medical advice.

## The Thanks Page

```text
src/app/components/Thanks.tsx    the page at #/thanks
src/app/components/LabRat.tsx    the illustration on it
```

Where someone lands after the beta form goes through. It sets expectations
honestly, which is the actual job of the page: the first thing it says is that
nothing will happen for a while and that silence is not a rejection. That one
line prevents most "did my form send?" emails.

It also lists whichever projects have an `appStoreUrl` under "While you wait,"
so a signup can turn into a download. That list builds itself from `projects.ts`
and needs no maintenance.

You can open `#/thanks` directly to work on it; it does not check that anyone
actually submitted anything.

### The lab rat

`LabRat.tsx` is a hand-drawn SVG on a 260 x 260 canvas, not an image file, so it
picks up the site's colors and can animate. The rat bobs, the liquid rocks, and
bubbles rise on staggered loops. The liquid uses the same gradient as the LABS
wordmark.

Landmarks, if you want to move something:

```text
y = 112    the beaker rim
y = 150    the liquid surface
(130, 62)  the centre of the rat's head
```

Two things are load-bearing and easy to break by reordering:

- **The paws are drawn after the rim.** Draw them before it and the 6px rim
  stroke cuts each paw in half.
- **The tail attaches at one point and ends in open air.** An earlier version
  curled back to touch the glass twice, which turned the beaker into a coffee
  mug. It sits on the left to stay clear of the spout.

## The About Page

```text
src/app/components/About.tsx    the page at #/about
```

const FOUNDER_PHOTO    = null;   // '/brand/your-photo.jpg' once you add one
const FOUNDER_NAME     = 'Jarred M. Carter';
const FOUNDER_ROLE     = 'Founder';
const FOUNDER_TAGLINE  = '...';  // one or two sentences under your name

### Adding your photo

1. Put the file in `public/brand/`.
2. Set `FOUNDER_PHOTO` to its path, starting with a slash:

   ```ts
   const FOUNDER_PHOTO: string | null = '/brand/jarred-carter.jpg';
   ```

3. Update `FOUNDER_PHOTO_ALT` to describe the picture for anyone who cannot see
   it.

A portrait crop around 4:5 fits the layout, at least 1000px on the short edge.

it never shows a broken image.

`FOUNDER_BIO` is an array of strings and each one becomes its own paragraph. Add

placeholder text starts with "REPLACE ME" so it is obvious on the page if you
ship before writing it.

To drop the "How the apps get built" section entirely, empty the `PRINCIPLES`
array. The section disappears rather than leaving an empty heading.

## The Beta Signup Form

```text
src/app/components/EarlyAccess.tsx    the page at #/early-access
```

This is the page "Get Early Access" opens. It explains why testers matter, what
testing actually involves, and collects enough detail to know whether a build
will even run on someone's hardware.

### Where submissions go

The site is static, and GitHub Pages cannot receive a form post, so submissions
go through Formspree and land in `retrac.labs@gmail.com`. The endpoint is at the
top of `EarlyAccess.tsx`:

```ts
const FORMSPREE_ENDPOINT = 'https://formspree.io/f/mnpqkgqo';
```

**The free tier is 50 submissions a month across the whole Formspree account,
not per form.** That number is shared with any other form you add later, so
check the Formspree dashboard before assuming a quiet week means no interest.

### Ignore Formspree's "Redirect" setting

In the Formspree dashboard, under **Workflow**, there is an *If submission
success -> Redirect* field locked behind the Personal plan. **You do not need
it, and upgrading for it would buy you nothing.**

That setting only applies to a plain HTML form post, where the browser navigates
to Formspree and Formspree sends it back with a 302. This form does not work
that way. It posts through `fetch()` with an `Accept: application/json` header,
so Formspree replies with JSON, the browser never leaves the site, and
`EarlyAccess.tsx` decides what happens next:

```ts
if (response.ok) {
  window.location.hash = '#/thanks';
}
```

The thanks page is ours, it is instant, and it works on the free tier.

### CAPTCHA must be off, or the form cannot submit

**This one will cost you an afternoon if you forget it.** If Formspree's CAPTCHA
is switched on for this form, every submission is rejected with:

```json
{"error":"Please complete the Turnstile"}
```

Cloudflare Turnstile works by putting a widget on the page, which produces a
`cf-turnstile-response` token that rides along with the submission. This form
posts over `fetch()` and renders no such widget, so there is no token, so
Formspree refuses it. Nothing about the page is broken; the two settings are
simply incompatible as configured.

To turn it off: Formspree dashboard, open the form, find the **CAPTCHA** section,
**Adjust settings**, and disable it. Save.

The form is not left naked. Formspree still runs its own spam filtering, and the
form carries Formspree's `_gotcha` honeypot: an input positioned off-screen that
no human ever sees, so anything that fills it in is a bot and the submission is
dropped.

If you later decide you do want Turnstile, it means getting your own Cloudflare
site key and secret key, loading Cloudflare's script, rendering the widget on
the page, and adding Cloudflare to the privacy policy as another party that sees
visitor data. Worth it at volume. Not worth it at 50 submissions a month.

### When a submission fails

The visitor sees a sentence with Formspree's own reason in brackets, and the
full response is written to the browser console:

```text
[Retrac Labs] Formspree rejected the submission: 400 {error: "..."}
```

Open the console first. Formspree answers with either `{ error: "..." }` or
`{ errors: [{ message }] }` depending on the failure, and the page reads both.

### Formspree has its own spam folder

Separate from Gmail's. In the Formspree dashboard the form has **Inbox** and
**Spam** tabs, and a submission filed as spam does not count against the monthly
50. Test submissions from `localhost` tend to land there, which is expected and
not a sign anything is broken.

Check the Spam tab occasionally once the site is live. If a real signup is
sitting in it, mark it not-spam so the classifier learns.

### Testing the form

The only real test is a live submission, which does use one of your 50:

```bash
curl -sS -X POST https://formspree.io/f/mnpqkgqo \
  -H "Accept: application/json" \
  -F "email=test@retraclabs.co" \
  -F "notes=Connection test, ignore."
```

A healthy form replies `{"next":"...","ok":true}`. Note that checking the
endpoint with a GET tells you nothing: Formspree answers `405 Please submit POST
request` for a real form ID and a made-up one alike.

If that value is ever replaced with a placeholder, the page swaps the submit
button for an amber "this form isn't connected yet" panel and points people at
your email instead. That is deliberate: nobody should ever fill in a form that
quietly goes nowhere.

### What it asks

Email is the only required field. Everything else is optional, because a
half-filled form you actually receive beats a complete one nobody finishes.

```text
email, name, age range, industry, devices, device year, exact model,
macOS / iOS / iPadOS versions, apps of interest, time available,
feedback style, accessibility features used, region, free-text notes
```

### Editing the questions

The dropdowns and checkbox groups are plain arrays at the top of the file:

```ts
const AGE_RANGES = [...]
const INDUSTRIES = [...]
const DEVICES = [...]
const MAKE_YEARS = [...]
const APPS = [...]
```

Add or remove a line and the form updates. `APPS` in particular will drift, so
update it whenever a project is renamed from its codename.

`DEVICES` lists **product lines**, not model names ("iPhone", not "iPhone 17
Pro"). That is on purpose: a list of model names is out of date the week Apple
ships something, and the "exact model" text field below already catches the
detail from anyone who knows it. `MAKE_YEARS` is the only list that needs a new
entry each January.

`APPS` is not a list at all any more. It is built from the `projects` array, so
the checkbox for each project uses its `name` and its `teaser`:

```ts
const APPS = [
  ...projects.map((project) => ({ value: project.name, hint: ... })),
  { value: 'Whatever needs testers most', ... },
];
```

**So edit a teaser in `projects.ts` and both the card and the form update.**
There is no second copy to keep in sync, and a project added to the array shows
up on the form on its own.

Keep those teasers boring: a function, never a feature list. Saying an app does
transcription is not announcing it.

## Light Mode

The site is **dark by default for everyone**, and light is something a reader
opts into with the sun icon in the menu bar. It does not follow the operating
system's appearance setting, on purpose: the dark version is the brand.

```text
src/app/theme.ts                    reading, applying, and storing the choice
src/app/components/ThemeToggle.tsx  the button in the menu bar
src/styles/tailwind.css             where the `light:` variant is defined
index.html                          sets the class before React mounts
```

### How it works

Dark is the **unprefixed** palette, and light is an override:

```tsx
className="bg-zinc-900 light:bg-white"
```

That reads as "dark normally, white when asked", which matches the intent and
meant the whole site did not have to be rewritten light-first. The variant is
one line in `tailwind.css`:

```css
@custom-variant light (&:where(.light, .light *));
```

The class goes on `<html>`. An inline script at the top of `index.html` puts it
there **before React loads**, so somebody who chose light never sees a flash of
dark first. That script reads the same localStorage key as `theme.ts`; if you
change the key, change both.

### Adding new markup

Every color class you write needs a light counterpart. The mapping in use:

```text
bg-[#09090b]     light:bg-[#f4f4f5]     the page ground
bg-zinc-900      light:bg-white         a card
bg-[#0f0f12]     light:bg-zinc-50       an inset card
bg-zinc-800      light:bg-zinc-100      a pill
border-zinc-800  light:border-zinc-200
border-zinc-700  light:border-zinc-300
text-white       light:text-zinc-900
text-zinc-300    light:text-zinc-700
text-zinc-400    light:text-zinc-600
text-zinc-500    light:text-zinc-600    zinc-500 is 4.39:1 on light, just under AA
```

**Accents get darker on light, not lighter.** A 400-weight accent on white is
unreadable, so `text-cyan-400` pairs with `light:text-cyan-700`, and so on
through the palette in `src/app/data/accents.ts`.

### Two traps

**A button whose background does not change must keep its text color.** The
submit button is `bg-cyan-400` in both themes, so its black text has to stay
black. Adding `light:text-white` there drops it to 1.8:1. The same applies to
anything with a `hover:bg-yellow-400`: the hover fill stays yellow in both
themes, so the hover text has to be dark in both.

**Form fields need to be recessed on light, not white.** A white input on a
white card is separated only by a hairline. They use `light:bg-zinc-50` with a
`light:border-zinc-300` so the field still reads as a field.

### Checking your work

Paste this into the browser console on any page to audit contrast. It converts
through canvas because Tailwind 4 emits `oklch()`, which cannot be parsed as RGB:

```js
const cv=document.createElement('canvas');cv.width=cv.height=1;
const cx=cv.getContext('2d',{willReadFrequently:true});
const toRGB=s=>{cx.fillStyle='#000';cx.fillStyle=s;cx.fillRect(0,0,1,1);
  const d=cx.getImageData(0,0,1,1).data;return [d[0],d[1],d[2]];};
const lum=(r,g,b)=>{const f=c=>{c/=255;return c<=.03928?c/12.92:((c+.055)/1.055)**2.4};
  return .2126*f(r)+.7152*f(g)+.0722*f(b)};
[...document.querySelectorAll('p,h1,h2,h3,span,a,li,button')].forEach(el=>{
  const cs=getComputedStyle(el); if(!el.offsetParent) return;
  const t=[...el.childNodes].filter(n=>n.nodeType===3).map(n=>n.textContent.trim()).join('');
  if(t.length<3) return;
  let n=el,bg=[255,255,255];
  while(n){const c=getComputedStyle(n).backgroundColor;
    if(!c.includes('rgba(0, 0, 0, 0)')){bg=toRGB(c);break} n=n.parentElement}
  const L1=lum(...toRGB(cs.color)),L2=lum(...bg);
  const r=(Math.max(L1,L2)+.05)/(Math.min(L1,L2)+.05);
  if(r<4.5) console.warn(r.toFixed(2), t.slice(0,40), el);
});
```

Anything under 4.5 for body text, or under 3 for large text, fails WCAG AA.
Both themes should be checked; a fix for one can break the other.

## Cursors

The site uses the same pixel cursors as jarredmcarter.com: an arrow for the
page, a pointing hand for anything clickable. Same files, same hotspots, so
moving between the two sites feels like one place.

```text
public/cursors/        the PNGs, 1x and 2x
src/styles/cursors.css which cursor goes where
```

The floppy disk did not go away. It is now the **idle** cursor: sit still for a
couple of seconds and the pixel cursor disappears and the floppy fades in and
spins. Move the mouse and the pixel cursor comes back. Scrolling deliberately
does not count as moving, so someone reading down the page keeps the floppy.

To change how long that takes, edit one line in
`src/app/components/CustomCursor.tsx`:

```ts
const IDLE_MS = 2200;
```

The PNGs are generated by `tools/cursors.py` in the **jcart** repo, not this
one. To change the artwork, edit the pixel grids there, run it, then copy the
output over:

```bash
cp ~/Websites/jcart/assets/img/cursors/*.png ~/Websites/retraclabs.github.io/public/cursors/
```

Touch devices get the normal system cursor and no floppy at all.

## Styling Basics

Most styling is Tailwind CSS inside `className`.

Examples:

```tsx
className="text-white bg-zinc-900 p-6 rounded-2xl"
```

Common patterns:

- `text-white`: white text
- `text-zinc-400`: gray text
- `bg-zinc-900`: dark background
- `p-6`: padding
- `mt-6`: margin top
- `rounded-2xl`: rounded corners
- `border-2 border-zinc-800`: border
- `sm:`, `md:`, `lg:`: responsive breakpoints

Example:

```tsx
className="text-lg sm:text-xl md:text-3xl"
```

This means:

- mobile: `text-lg`
- small screens and up: `text-xl`
- medium screens and up: `text-3xl`

## Common Problems

### A project card is not clickable

That is probably correct. A project with its `summary` commented out is
unannounced, and unannounced projects have no page, so their cards are not
buttons. See "Hiding A Project Until It Ships." If it *should* be clickable,
uncomment its `summary`.

### The project page does not open

Check:

1. The slug exists in `projects.ts`.
2. That project has a `summary`. Without one it has no page by design.
3. `App.tsx` route matching still uses:

   ```ts
   /^#\/projects\/([a-z0-9-]+)$/
   ```

### The site is blank

Run:

```bash
npm run build
```

Read the first error. It is usually:

- a missing icon import in `projects.ts` (the most common cause)
- a bad import path
- mismatched JSX tags
- a missing or doubled comma in `projects.ts`

### The cards are in the wrong order

The array order in `projects.ts` *is* the page order. If a card is not where you
expect, its block is not where you think it is in that array.

### A row of cards looks lopsided

The `span` values in that row no longer add up to six. See "Reordering
Projects."

### The menu bar appears too early or too late

Edit `HERO_FADE_END` in `src/app/heroChoreography.ts`. Do not add a separate
threshold in `App.tsx`; the point of that file is that both components read the
same number.

### Text updates do not show

Hard refresh the browser. If needed, stop and restart:

```bash
npm run dev
```

### GitHub Pages does not update

Check:

1. GitHub Desktop pushed the commit.
2. GitHub Actions ran.
3. The deploy workflow completed successfully.
4. Browser cache is not showing the old site.

## Mental Model

Think of the site as three layers:

1. Data: `src/app/data/projects.ts` and `src/app/data/accents.ts`
2. Components/layout: `src/app/components/*.tsx`
3. Routing: `src/app/App.tsx`

The important habit: **most changes belong in layer 1.** Reordering projects,
hiding one, announcing one, renaming a codename, swapping an icon, changing a
tagline: all of that is `projects.ts` only. If you find yourself editing
`LabSection.tsx` to move a card, stop; you are in the wrong file.

Layer 2 is for changing how *every* card or page looks. Layer 3 is for adding a
new kind of page.

When in doubt, run:

```bash
npm run build
```

It catches most structural mistakes before GitHub does.
